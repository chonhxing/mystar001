# 审核风险与应对（附官方原文）

这份文档是给你做决策用的，不是法律意见。所有引用都来自微信官方文档，我把链接和原文都放上，
你可以自己复核。**结论先说：最大的风险不是技术，是"算命/占卜"类内容被拒。**

---

## 一、最高风险：内容被判定为"测试类内容"

**来源**：[微信小程序平台常见拒绝情形](https://developers.weixin.qq.com/minigame/product/reject)
（小游戏与小程序共用这套规范，页面标题写的是"小程序平台"）

原文，第 3.2.4 条：

> 3.2.4 小程序的页面内容中，不能存在测试类内容；示例：**算命，抽签，星座运势等**。

同文档 3.2.8.7：

> 3.2.8.7 小程序内容不能包含煽动民族仇恨、民族歧视、破坏民族团结的内容、破坏国家宗教政策、**宣扬邪教和封建迷信的**；

### ⚠️ 一个反直觉的坑：「星座运势」不能用作替换目标

很容易这样想：既然"占卜/算命"敏感，那换成"星座运势"总该安全了吧？

**恰恰相反 —— 「星座运势」是官方点名的三个示例词之一，是禁止列表里的一员，不是安全词。**
用它去替换等于从一个坑跳进更深的坑。

官方原文（同一条 3.2.4）：

> 小程序的页面内容中，不能存在测试类内容；示例：算命，抽签，**星座运势**等。

同一条里被点名的三个词是「算命、抽签、星座运势」，**这三个才是最高危的**。

**所以正确的做法是"去玄学化"——把词换成完全中性的说法：**

| 不用 | 用 | 出现在哪 |
| --- | --- | --- |
| 占卜 | 匹配 | 全站主按钮 |
| 算命 / 算卦 | 性格分析 | 类目与简介 |
| 抽签 / 一签 | 随机匹配 / 结果 | 快捷入口 |
| 运势 | 今日提示 | 每日模块 |
| 吉凶 / 大吉 | 状态 / 顺畅 | 提示等级 |
| 命盘 | 图谱 | 结果页 |
| 神谕 | 一句提点 | 结尾文案 |
| 占星 | （已从品牌名移除） | 标题 |

这张表就是 `config/copy.js` 里的 `SAFE_WORDING`，改它等于改全站口径。
`npm run check` 会把上面左列的词当**失败项**扫描（包括"星座运势"本身）。

### 这条对我们意味着什么

"星座""运势""抽签""算命"这些词是**白纸黑字被点名的**。我们的产品形态（看生辰 → 出命盘 → 给你一段解读）
天然贴着这条线。**如果按原样提审，被拒的概率不低。**

### 我做了什么（已经改在代码里）

1. **高风险词集中收口**：所有用户可见文案统一从 `config/copy.js` 出，
   里面有一张 `SAFE_WORDING` 替换表，把高风险词映射到安全表述：

   | 高风险词 | 现在用的表述 |
   | --- | --- |
   | 占卜 | 匹配 |
   | 算命 / 算卦 | 性格分析 |
   | 抽签 / 一签 | 随机匹配 / 结果 |
   | 运势 | 今日提示 |
   | 吉凶 / 大吉 | 状态 / 顺畅 |
   | 预言 | 提示 |
   | 命盘 | 命途图谱 |
   | 神谕 | 一句提点 |

2. **静态检查会拦**：`npm run check` 会扫描用户可见文案和小游戏场景代码，
   出现"占卜/算命/抽签/运势/吉凶/预言"就直接失败。写死一个词都会被挡住。

3. **包装成"角色匹配 + 收集"**：核心循环是"答 9 题 → 匹配到一个角色 → 收集进图鉴"，
   而不是"输入生辰 → 预测你的命运"。这个叙事更靠近"性格测试/收集游戏"。

4. **AI 提示词里也做了同样约束**：`server/prompts.js` 明确禁止模型输出
   疾病/寿命/死亡、投资彩票、婚育预言、宿命论式贬低。

### 还需要你决定/做的

- [ ] **品牌名**：现在叫「我推的星运」，`占星` 在敏感区间。备选见 `config/copy.js` 的 `BRAND.SAFE_NAME`。
      改名成本是一行代码，但 MP 后台名称、备案主体名要你自己改。
- [ ] **提审前把"命途图谱"这类词再过一遍**：如果审核员较真，"图谱"也可能被追问，
      最保守的说法是"性格坐标"。这个尺度你自己把握。
- [ ] **准备被拒一次**：第一次提交很可能被打回，按反馈改表述再提。这是常态，不是代码问题。

## 二、类目风险：游戏类目不可逆

**来源**：[常见拒绝情形 2.1.3](https://developers.weixin.qq.com/minigame/product/reject)

> 2.1.3 你需根据实际提供服务范围慎重选择服务类目，一旦你选择了游戏类目，
> 该类目将不可修改变更为其他小程序类目。

同时注册小游戏账号时（[新手教程](https://developers.weixin.qq.com/minigame/dev/guide/develop/start.html)）：

> 选择类目时选择游戏类目，选择游戏类目后，该账号即为小游戏账号（无法更改一级类目，谨慎选择）

**应对**：这就是我在仓库里**同时保留小程序版**（`miniprogram/`）的原因。
小游戏账号一旦建成就是游戏类目，如果因为内容问题过不了，小程序版可以换个类目路径去提审，
两者共享同一套算法、数据、后端，不会白做。

## 二点五、⚠️ 运营规范里**直接点名"算命类"**的一条

**来源**：[平台运营规范 5.18 内容安全](https://developers.weixin.qq.com/minigame/product/)

原文：

> 5.18 小程序涉及未设置过滤违法、违规等不当信息内容的机制。必须调用内容安全检测接口
> 校验文本/图片是否含有敏感内容……
>   5.18.2 **昵称测试/算命类 UGC 小程序**，小程序内可任意输入敏感违规内容，无安全过滤的。

这条有两层含义，都要注意：

1. **好消息**：平台把"算命类小程序"当成一个**已知且在管的存在**，规则针对的是
   "无内容过滤机制"，而不是"不能做这类产品"。这印证了我们的判断：换表述 + 做好过滤就能过。
2. **红线**：**只要用户能自由输入文字并展示或上传，就必须接内容安全检测接口。**

**我们的现状与边界**：

| 场景 | 现状 | 是否必须接 `msgSecCheck` |
| --- | --- | --- |
| 用户输入「称呼」 | 只存用户手机本地，**从不上传、不展示给别人** | 否 |
| 命盘数值送 AI | 只发匿名数字，不带任何自由文本 | 否 |
| ⚠️ 以后加"写一句话让 AI 解读" | 用户自由文本会进 AI 和后端 | **是，必须** |
| ⚠️ 以后做"命盘昵称公开/排行榜显示昵称" | 他人可见 UGC | **是，必须** |
| ⚠️ 以后做"用户生成分享图带昵称" | 图片含用户内容 | **建议，图片也要过 `imgSecCheck`** |

**结论：现在的设计恰好绕开了这条**，这是"不上传自由文本"这个决定的额外红利。
但它是**一条边界，不是一个永久豁免** —— 加任何 UGC 功能前都要回来补内容安全校验。

## 二点六、体验红线（运营规范 2.9 / 2.10）

这几条的处罚很重（封禁分享能力、封禁跳出/新进能力、直至下架），逐条对照：

| 条款 | 要求 | 我们 |
| --- | --- | --- |
| 2.9.1 | 分享卡片的文案、图片**与游戏内容无关** → 封禁分享 3~30 天直至永久 | ✅ 分享文案就是角色名 + 共振度，强相关 |
| 2.10.1 | 首屏必须能正常"开始游戏"，不可直接弹第三方跳转；**不允许任何形式的误触** | ✅ 首屏就是表单 + 两个按钮 |
| 2.10.2 | 广告不可遮挡"开始/继续游戏"按钮，不可欺骗/误导点击 | ✅ 广告只在用户主动点击后播放 |
| 2.10.3 | 发布状态的小游戏**必须可正常体验** | ✅ 后端挂了也能玩（本机降级） |
| 5.1.1 | **强制分享**（分享后才能继续下一步/解锁功能） | ✅ 分享按钮不给任何奖励 |
| 5.8 | 禁止"利用隐藏小程序的**测试内容**等方式绕过审核" | ✅ 项目内**没有**自检/调试场景，`npm run check` 会硬检查（文件名以 smoke/demo/test/debug 开头的场景会直接报错） |

## 三、内容安全（AI 生成部分）

**来源**：[平台运营规范 5.18 内容安全](https://developers.weixin.qq.com/minigame/product/)，
以及 [小游戏隐私合规开发指南](https://developers.weixin.qq.com/minigame/dev/guide/open-ability/privacy.html)

关键点：
1. **AI 生成内容必须标识**。《人工智能生成合成内容标识办法》2025-09-01 起施行，
   我们在结果页底部有固定标识（`config.ADS` 旁边的 `SHOW_AI_LABEL` 控制，**建议不要关**）。
2. **生成式 AI 服务面向公众提供需要备案**。接入已备案的第三方模型能降低合规成本，
   但你自己是服务提供者这一点不变 —— 请咨询法务。
3. **用户输入内容需要过内容安全接口**（`msgSecCheck`）。
   我们目前**没有让用户自由输入文本进 AI**（只发匿名数字），所以暂时不需要。
   但如果以后加"用户写一句话让 AI 解读"，**必须**接入内容安全校验。

### 我在代码里做的防护（`server/validate.js`）

AI 输出会逐字段过一遍守门规则，命中就退回本机模板：
- 长度不合规 → 退回那一段
- 违禁内容（AI 自指、模型名、疾病、投资收益承诺、自伤、羞辱性宿命论）→ 退回那一段
- 出现**编造的作品名**（不在允许列表里的《XXX》）→ 整批判为不可信，全部退回模板

### 虚拟支付（做内购才需要看）

**开通门槛**（官方《虚拟支付进件》原文）：企业/个体工商户主体 + 已接入中宣部实名认证系统
+ **版号、软著、自审自查报告及相关授权**。没版号就开不了，所以现在默认关闭。

**iOS 从"禁止"变成了"有条件支持"**（容易过时的一条，以官方为准）：
Android/Windows/OHOS 默认支持；iOS 需要 iOS 15+ / 基础库 3.10.3+ / 客户端 8.0.68+，
且**苹果支付不支持沙箱环境**。错误码 `701001` = "ios 禁止支付"。
所以必须用 `wx.checkIsSupportMidasPayment` 先探测再拉起，老 iOS 用户只能走广告。

**未成年人保护（这是硬要求，不能绕过）**：
- 开通虚拟支付必须接入中宣部实名认证系统 → 平台会用**腾讯健康系统**统一管限额
- 错误码 `-15009` 就是"由于健康系统限制，本次支付已超过限额"，**官方会自动弹提示**，
  我们不要自己再弹一遍（重复提示很烦，而且可能与平台话术冲突）
- 未成年人的充值和游玩时长都受系统限制，不要试图绕过

**退款与客服**：涉及收费就必须有可用的客服入口。目前`server` 侧没有接客服消息，
上线前要补（`wx.openCustomerServiceConversation` 或客服消息接口）。

## 四、隐私与个人信息

**来源**：[小游戏隐私合规开发指南](https://developers.weixin.qq.com/minigame/dev/guide/open-ability/privacy.html)

官方要求：如果处理用户个人信息，需要在 MP 后台配置《用户隐私保护指引》，
并在 C 端做隐私授权交互 + 上报授权结果。

### 我们的现状

| 数据 | 去哪了 | 能否反推身份 |
| --- | --- | --- |
| 姓名 / 出生日期 / 出生时间 / 出生地 | **只存在用户手机本地**（`wx.setStorageSync`），不上传 | — |
| **微信昵称 / 头像** | **只存在用户手机本地**，不上传（见下面的专节） | 头像能对到人，所以**必须写进隐私指引** |
| 八轴分数、星座下标 | 开启 AI 解读时上传到我们自己的后端 | **不能**：多对一映射，枚举不出唯一生日 |
| **干支四柱** | 开启 AI 解读时**随那次请求发给模型服务** | ⚠️ **能**，见下面的更正 |
| 账号里的游玩记录 | 存服务端（角色 id、共振度、时间） | **不能**，只是游戏结果 |
| 分享链接 | **不含任何命盘数据**，只带入口 | — |

### 微信昵称头像（**上线前必须在后台配**）

**做了什么**：账号页顶部显示用户的微信头像和昵称，首页顶栏也跟着显示。

**⚠️ 上线前必做**：在 MP 后台《用户隐私保护指引》里**声明收集「微信昵称、头像」**。
没声明的话平台会直接拦掉这次调用 —— 表现是"用户点了按钮什么也没发生"，很难查。
代码里已经做了预防（`services/wechatprofile.js` 的 `ensurePrivacy()` 先要授权、
失败给明确提示），但"声明"这一步只能在后台做。

**政策背景（别照抄老教程）**：**2022-10-25 起，`wx.getUserInfo` / `wx.getUserProfile` /
`open-type="getUserInfo"` 全部被收回**，昵称固定返回「微信用户」、头像是灰色默认图。
现在唯一合规的路子是**让用户自己选**：

| 端 | 用的 API | 说明 |
| --- | --- | --- |
| 小程序 | `<button open-type="chooseAvatar">` + `<input type="nickname">` | 基础库 2.21.2+；拿到的是**临时路径**，必须 `saveFile` 才能长期用 |
| 小游戏 | `wx.createUserInfoButton` | 小游戏**没有** chooseAvatar 的等价物（`wx.createChooseAvatarButton` 文档 404） |

**代码里的三道防线**：
1. **匿名识别**（`isAnonymous`）：头像为空、或是官方那张灰图，就当"没拿到"，
   **不写库、不显示**，并如实告诉用户。给用户看一个灰色默认头像，还不如显示我们自己的徽记。
   判定**只看头像、不看昵称** —— 用户完全可以把自己叫「微信用户」，不该因此丢掉他的真头像。
2. **不上传**：头像只在本机。传到自己服务器就等于"收集用户的图片"，
   要写进指引、要给对象存储、要处理删除请求 —— 为一个装饰性圆头像不值。
   想同步见 `config.ACCOUNT.UPLOAD_AVATAR` 的注释（打开前先想清楚上面这三件事）。
3. **可关闭**：`config.ACCOUNT.ENABLE_WECHAT_PROFILE = false` 就完全回到没有头像的状态。

**填指引时的建议写法**：「收集：微信昵称、头像；用途：在个人中心展示；
是否上传服务器：否；是否共享给第三方：否；用户可随时更换或不使用」。

### 隐私弹窗：已按官方「自定义弹窗」模式接好（2026-09）

官方接口（基础库 2.32.3+，[wx.onNeedPrivacyAuthorization](https://developers.weixin.qq.com/minigame/dev/api/open-api/privacy/wx.onNeedPrivacyAuthorization.html)）：

- 注册监听后进入**自定义隐私弹窗模式**：隐私接口被调用时平台不再弹统一弹窗，
  而是触发我们的回调，由我们弹自己的授权窗，**用户点「同意/拒绝」时调 resolve**
  （官方硬性要求：resolve 必须挂在用户点击上，且要传 `{ event: 'agree' | 'disagree' }`）。
- 已接入的位置：`services/privacy.js`（监听与结算）、`src/js/ui/agreement.js`
  （授权窗 UI）、`src/js/boot.js`（启动即注册监听，早于任何隐私接口调用）。

**需要你在 MP 后台做的一步**：《用户隐私保护指引》里**声明收集「微信昵称、头像」**，
否则 `getPrivacySetting` 永远返回"不需要授权"，我们这一整套弹窗就不会被触发
（不是代码问题，是后台没声明）。

### 用户协议与隐私政策弹窗（提审要件）

- **首次启动**弹出协议窗：必须勾选「我已阅读并同意」才能继续；不同意可以退出游戏。
  同意状态持久化（`agreement_v1`），之后不再打扰。
- 账号页的**登录**和**头像授权**前各有一次闸门检查（覆盖"首启弹窗被跳过"的边角情况）。
- 设置页新增「用户协议与隐私政策」入口：**应用内随时可回看全文**（提审要求）。
- 全文在 `config/copy.js` 的 `LEGAL.userAgreement` / `LEGAL.privacyPolicy`：
  说清了收集什么、存哪里、不收集什么、未成年人与免责条款。
  上线前把里面的联系邮箱换成真实可用的地址。

### ⚠️ 更正：此前"生辰不出手机"的说法不准确

**干支四柱可反推出生时刻。** 四柱 → 年月日时是唯一确定的映射，枚举即可还原
（实测：用四柱枚举 1940–2015，命中 `1996-08-19 07:00` 与 `08:00`，实际 07:20 落在同一时辰）。
**所以四柱等价于生辰。**

准确的说法是三句：

1. ✅ **我们自己的服务端不落库任何生辰字段** —— `server/playlog.js` 有字段白名单，
   四柱 / 八轴 / 命盘种子 / 姓名 / 城市全部丢弃（有测试断言）
2. ✅ **账号里的游玩记录只存结果**（角色 id、共振度、稀有度、时间），推不回生日
3. ⚠️ **但发给 AI 的那一次请求里含四柱** —— 四柱是解读的核心素材

**这个取舍由你决定**，开关是 `config.PRIVACY.SEND_PILLARS_TO_AI`：
- `true`（默认）：解读更准，代价是模型服务能看到可反推生辰的数据
- `false`：只发星座 + 八轴数值。解读会少一层"日主/四柱"的意象，但上行数据就真的推不回生日

**填《用户隐私保护指引》时要注意**：保持默认的话，第三方模型服务会接触到
可反推出生时间的数据，这属于"向第三方提供"，**应当如实披露**。想省掉这层麻烦就关掉开关。

**关于界面上的合规声明**：为保持界面简洁，个人资料页不放说明性小字，
但《用户隐私保护指引》相关内容保留在「设置 → 关于」的弹窗里（用户能查到），
结果页底部也保留 AI 生成标识 —— **这两处不要删**。

**需要注意的点**：
- 出生日期 + 出生时间属于**个人信息**。虽然不上传，但**仍然要在《用户隐私保护指引》里披露**，
  因为"收集、存储"发生在用户设备上，而你是服务提供者。
- 建议在 MP 后台如实填写"收集：出生日期/时间；用途：本机算法计算；是否上传：否；是否共享：否"。
- 如果以后加云端存档，**必须**回来改这里 + 配置文件上传接口的隐私声明。别为了"数据好看"加上云端同步。

## 七、版权（角色库）

现在角色库里是**真实作品的角色名**，但：
- ✅ 只用了**名称类事实性标识**（角色名/作品名），没有官方立绘、截图、台词、Logo
- ✅ 所有描述文字（`motif` / `signature`）都是**我原创写的**
- ✅ 没有引用任何官方台词、没有真实声优/演员姓名

**风险判断**：
- 小规模、非商业、娱乐向：通常问题不大
- **商业化运营（广告变现也算商业化）前，建议取得授权，或整体替换为原创角色**

替换成本很低：`data/characters.js` 是独立数据表，换掉它不影响任何逻辑，
`npm run test:core` 会检查新角色表是否还满足"每根轴都有人站两端"的覆盖要求。
