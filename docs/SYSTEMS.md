# 我推的星运 · 系统功能说明（提审用）

> 本文档按提审要求逐个介绍游戏内系统。每个系统都写清三件事：
> **玩家看到什么 / 怎么用 / 涉及钱的地方怎么算**。
> 所有描述与线上代码一致，代码位置也标了出来，便于核对。
>
> ⚠️ 阅读顺序建议：先看第一节「本游戏**没有**的系统」——它直接回答审核最关心的几个点。

## 一、本游戏**没有**的系统（先说清楚，省得找）

| 常见的商业化系统 | 本游戏 |
| --- | --- |
| 游戏货币（元宝 / 金币 / 钻石 / 点券等） | **没有**。游戏内不存在任何可购买、可累积、可交易的虚拟货币，也没有任何数值化的货币概念 |
| 商城 / 商店 / 商品列表 | **没有**。不存在商品页、购物车、限时折扣 |
| 兑换码 / 礼包码 / 激活码 | **没有**。没有任何兑换入口 |
| 红包 / 返现 / 提现 | **没有**。不存在任何形式的现金回馈、红包发放或提现功能 |
| 转盘 / 抽奖 / 开箱 / 概率抽取 | **没有**。角色匹配是算法确定性的结果，**不涉及任何付费概率抽取** |
| 排行榜 / 好友对战 / 社交攀比 | **没有**。不存在排行榜，也没有任何"分享给奖励"的设计 |
| 体力 / 精力 / 冷却时间 | **没有**。不存在随时间恢复的体力机制 |

（见第四节）。

## 二、核心体验系统

### 1. 命途图谱与角色匹配系统

**系统说明（可直接填表）**：
玩家填入出生日期、时辰与出生地后，系统在本机把多源特征（太阳与月亮黄经、按出生地
经纬度估算的上升点、传统干支历法的年/月/日/时柱、生命灵数）按权重加权成一张
八轴的"命途图谱"，每根轴取 0~100 的数值；再与 60 个动漫、影视、游戏角色的
同结构图谱做**形状匹配**，得出最相似的一个角色（主推）、两个次相似角色，
以及一个最不相似的相反命途。

- **玩家看到什么**：结果页展示八轴坐标条、命途图谱全相、主推角色的共振度百分比、
  "为什么是 TA"的对比解读、以及"没有带入的命途"。
- **怎么保证不总是同一个人**：匹配按八轴向量做**形状**比对（z-score 归一），
  而不是原始数值距离；另有稀有度惩罚与镜像反向逻辑，实测 60 个角色全部会出场、
  最高频角色占比低于 12%。
- **是否受付费影响**：**完全不受影响**。付费与广告只决定"能不能再玩一次"，
  不改变算出来的结果，也不存在"付费看更好的结果"。
- 代码：`core/chart.js`、`core/matcher.js`、`core/vector.js`

### 2. 问答修正系统（题库）

**系统说明**：
一次匹配可以搭配 10 / 20 / 30 / 50 道没有标准答案的选择题，用来微调图谱。
题目从 1113 道题库中**按八根轴分层抽样**（保证只答 10 道也覆盖全部八轴），
其中 131 道是多选题，每题选项数量不固定（2~6 个）。用户可以跳过任意一题，
也可以一键跳过全部；跳过的题不产生任何影响。

- **每题影响力已做归一**：答 50 道与答 10 道对图谱的总影响力相同，
  多答只是让结果更准，不会把图谱推向极端。
- **可玩性**：题库每次随机抽取，同一个人每次玩到的题目不同。
- 代码：`core/quiz.js`、`data/questions/`

### 3. 图鉴收集系统

**系统说明**：
玩过的角色会进入图鉴。图鉴列出全部 60 个角色，按"是否已遇见"区分显示，
并记录每个角色**首次遇见的时间**与**遇见次数**；角色分传说 / 史诗 / 稀有 / 寻常
四档稀有度，用不同颜色区分。未遇见的角色显示为剪影，不剧透名字与作品。

- **数据存哪**：本机一份，账号里一份（只存角色 id、共振度、时间，不存任何生辰信息）。
- **跨设备**：换设备后用同一个微信登录，可以一键从账号恢复图鉴进度。
- 代码：`src/js/scenes/codex.js`、`utils/storage.js`

### 4. 匹配记录系统

**系统说明**：
每次匹配都会在"记录"里留一条，包含当时的角色、共振度、图谱最突出的一轴、
以及这次是"本机计算"还是"AI 深化解读"。点任意一条可以回到该次结果的角色详情。
记录支持一键清空。

- **数据边界**：记录里**不含**出生日期、时辰、出生地、姓名，也不含图谱种子，
  所以即使记录被看到也推不回本人信息。
- 代码：`src/js/scenes/records.js`、`services/playlog.js`

### 5. 个人资料卡系统

**系统说明**：
用户可以把一份出生资料保存成"资料卡"，最多存 10 张（自己、家人、朋友各存一份），
下次想再玩时**一键选卡直接进入答题**，不用重新填。
每张资料卡显示称呼、出生日期、时辰是否已知、出生地（三级地区）。

- **数据边界**：资料卡**只存本机**，不上传服务器，与游戏账号解耦
  （账号里只有游玩结果，没有生辰）。
- 代码：`src/js/scenes/account.js`、`utils/storage.js`

### 6. 游戏账号系统（无注册、无密码）

**系统说明**：
用微信静默登录：进入游戏时调用 `wx.login` 拿一次性 code，服务端用
`code2session` 换成账号标识，**用户不需要注册、不需要输密码、不需要授权手机号**，
进入游戏即已登录。账号的作用只有一个：让充值、解锁的角色和游玩记录跟着账号走。

- **账号里存什么**：游玩结果（角色 id、共振度、稀有度、时间、解锁集合）、
  开通记录、剩余额度。
- **账号里不存什么**：姓名、出生日期、时辰、出生地、图谱种子、八轴数值 ——
  服务端有字段白名单，这些字段即使被上报也会被丢弃（有测试断言）。
- **用户能做什么**：查看账号状态、从账号恢复记录、清空账号记录。
- 代码：`server/wxauth.js`、`server/playlog.js`、`services/account.js`

### 7. 昵称头像系统（可选，用户主动选择）

**系统说明**：
用户可以在个人中心选择是否使用自己的微信头像和昵称。**必须由用户主动点击按钮**
才会读取，游戏不会在启动时索取；不选择也完全不影响游戏。
出于合规与隐私考虑，头像与昵称**只保存在用户本机**，不上传服务器，
也不共享给任何第三方。

- 政策依据：2022-10-25 起微信已收回 `getUserInfo` 系列的昵称头像能力，
  现在只能通过用户主动选择的方式获取（小游戏用 `wx.createUserInfoButton`，
  小程序用 `chooseAvatar`）。代码里会识别"匿名返回"（默认灰色头像）并如实告知用户。
- 代码：`services/wechatprofile.js`

## 三、内容与体验系统

### 8. 今日提示系统

**系统说明**：
填过生辰的用户，主界面会显示一张"今日提示"卡片：当天的状态分档、一句提示语、
宜做与忌做各一条、幸运色、幸运数字、幸运物，以及"今天最突出的一轴"。
内容由本机算法按当天日期生成，不联网、不推送。

- 代码：`core/fortune.js`

### 9. 解读文案系统（AI 中转 + 降级 + 明确标识）

**系统说明**：
结果页的文字解读由服务端中转生成：客户端只上传**匿名数值**（八轴分数、星座与干支的
下标、答题统计），**不上传**姓名、出生日期、时辰、出生地。
服务端有 30 天缓存（同一图谱不重复生成）、每日配额与限流；
如果服务不可用，会自动降级为本机模板文案，**不影响出结果**。

- **合规标识**：结果页底部明确标注"本页解读文案由人工智能生成"，
  并在界面与文档中提示"结果仅供娱乐"。该标识不可删除。
- **可关闭**：用户可在设置里关闭 AI 解读，关闭后完全在本机完成、不联网。
- 代码：`services/divination.js`、`server/index.js`、`server/prompts.js`

### 10. 版本更新系统

**系统说明**：
启动时检查是否有新版本，检测到新包会在后台异步下载，下载完成后用平台原生弹窗
询问用户是否重启应用；用户选择稍后也不会影响当前游玩。
代码：`services/update.js`

### 11. 分享系统（**不给任何奖励**）

**系统说明**：
用户可以把结果分享给微信好友或群。分享内容是**纯文字标题 + 游戏入口**，
**不携带任何图谱数据或个人信息**（不泄露对方的匹配结果）。
按平台运营规范，**分享不发放任何奖励**，也不做"分享后解锁"这类设计。
代码：`services/share.js`

## 四、涉及商业化的系统（**这一节请重点看**）

游戏内只有两处与商业化相关：**激励视频广告**和**畅玩卡**。两者都建立在
同一个前提上 —— 先送的 2 次免费额度用完。

### 12. 使用额度系统（免费次数）

**系统说明**：
每位用户**免费送 2 次**完整匹配，用完才需要"看一次广告"或"开通畅玩卡"。
额度只决定"能不能再玩一次"，**不改变结果内容**，也不存在"付费抽更好的角色"。
免费次数**只存本机**，不需要登录也能用。

- **优先级**：畅玩卡 > 免费次数 > 广告解锁券 > 需要看广告/开通
- **重要口径**：2 次是**一次性**的体验额度，**不按天重置**（代码里 `freeUsed` 只增不减，
  没有任何按日归零的逻辑）。所以描述里不能写"每天送 2 次"。
- 代码：`services/entitlement.js`、`services/gate.js`

#### 可直接复制的描述（按表单字数选一条）

**① 精简版（65 字，满足"最少 30 字"）**

> 每位用户免费赠送 2 次完整匹配，一次性发放、不按天重置；用完可通过观看激励视频广告或开通畅玩卡继续，免费次数不影响匹配结果。

**② 标准版（约 195 字，推荐）**

> 每位用户免费赠送 2 次完整的性格图谱匹配，属于一次性的体验额度，用完不会按天重置。2 次用完后，玩家可以完整观看一次激励视频广告获得 1 张解锁券，或开通畅玩卡在有效期内无限次匹配，也可以随时停止使用，不产生任何费用。免费次数只决定玩家能否继续匹配，不改变匹配结果内容，也不存在付费抽取更好角色的设计。免费次数保存在用户本机，无需登录即可使用；若已开通畅玩卡，则优先使用畅玩卡，不会扣减免费次数。

**③ 逐项填表版**

| 字段 | 填写内容 |
| --- | --- |
| 系统名称 | 免费体验次数 |
| 是否收费 | **否**，免费赠送 |
| 赠送次数 | 2 次完整匹配 |
| 是否按天重置 | **否**，一次性发放，用完不再有 |
| 是否需要登录 | 否，未登录也可正常使用 |
| 用完后的选择 | 看激励视频广告得解锁券 / 开通畅玩卡 / 停止使用（无任何强制） |
| 是否影响匹配结果 | **不影响** |
| 消耗优先级 | 畅玩卡 > 免费次数 > 解锁券 |
| 存储位置 | **本机** |

#### ⚠️ 界面文案与真实行为不一致（提审前必须统一）

游戏界面在额度用尽时会显示「**今天的**免费次数用完了」
（`copy.UI.unlockTitle`，渲染在 `src/js/ui/unlock.js:156`），但代码里免费次数
**没有任何按天重置逻辑** —— `freeUsed` 只在消耗时 +1，唯一的重置入口是测试用的
`entitlement.reset()`。也就是说**第二天不会重新送 2 次**，用户会白等一天。

这属于"说明与事实不符"，两个方向二选一：

| 选择 | 改动 | 影响 |
| --- | --- | --- |
| **改文案（推荐）** | 把 `copy.UI.unlockTitle` 改成「免费次数用完了」 | 一行改动；与现在的模型一致（免费仅 2 次） |
| 改成真的按天送 | 给 `freeUsed` 加日期标记，跨天归零 | 更慷慨、留存更好，但要定"一天"的口径（时区、本机时间可被篡改），变现变弱 |

**已按事实统一**（2026-09-17）：界面文案改成「免费次数用完了」——
原来写的是「**今天的**免费次数用完了」，而代码里没有任何按天重置逻辑，
用户会白等一天。提审材料也按「一次性 2 次」写，不写「每日 2 次」。

#### 存放位置（涉及"用户会不会丢东西"）

| 权益 | 存哪 | 换设备 |
| --- | --- | --- |
| 免费次数（2 次） | **只存本机** | 新设备重新给 2 次（等于新用户额度） |
| 解锁券 | **只存本机** | 不跨设备（它不是付费资产，丢了不影响已购权益） |
| 畅玩卡（付费） | **以服务端为准**，本地只是缓存 | 应当能找回 —— 但见第 14 节的缺口 |

代码注释写得很清楚：*"涉及钱的权益以服务端为准（见 server/pay.js），本地只是缓存。
免费次数和广告券不涉及钱，留在本地就行。"*

> 顺带一个已知的宽松点：因为存在本机，**用户清缓存或换设备会重新获得 2 次免费次数**。
> 这不构成收入损失（免费额度本身不收费），但如果以后想严格控制，需要把额度挪到服务端。

### 13. 激励视频广告系统

**系统说明**：
免费次数用完后，用户可以选择**观看一次完整的激励视频广告**，换取 1 次解锁机会。
必须**完整播放结束**才发放奖励（中途关闭不发放，这是平台硬性规则），
不存在自动播放、诱导点击或误触区域。

- **设计规则**：一次广告 = 确定的 1 次机会，不是抽奖、不叠加倍率。
- **合规**：不做"分享给奖励"，不做"看广告抽奖"，不做任何形式的诱导分享。
- 代码：`services/reward.js`

**⚠️ 当前实际行为（已按下面的方式处理）**：

线上配置是 `ADS.ENABLED = false` 且广告位 ID 为空。代码里为了**不让流程卡死**，
在"拿不到广告实例"时会**直接发放一次解锁**（`src/js/ui/unlock.js` 的 `byAd()`，
原注释就写着"提审前要确认，否则这等于免费无限"）。

也就是说：**现在的线上版本，免费 2 次用完后点一下"看广告解锁"就会直接拿到机会，
既不播广告也不收钱** —— 相当于无限免费。这在提审时有两个风险：
① 提交材料里写了有广告变现，但实际没有广告，属于描述不符；
② 审核员点那个按钮会看到"没有广告直接给奖励"，可能被判为虚假入口。

**二选一（代码已经支持，改配置即可）**：

| 选择 | 怎么做 |
| --- | --- |
| 打算做广告变现 | 先在 MP 后台开通流量主、创建激励视频广告位，把 ID 填进 `config.ADS.UNITS.divinate_again` 并打开 `ADS.ENABLED` |
| 暂不做广告 | 把 `config.ADS.GRANT_WHEN_UNAVAILABLE` 改成 `false`（一个开关，解锁面板和充值页同时生效），并把简介里的变现描述去掉 |

**现在的默认行为**：广告位没配时**仍然发放一次**，但界面会如实提示
「广告位暂未开放，这次先送你一次」—— 用户知道为什么白得一次，不会以为按钮坏了，
审核同学点这一下也不会卡住。

开关是 `config.ADS.GRANT_WHEN_UNAVAILABLE`（`false` = 没广告就明确不给）。
**策略只有一处**（`services/reward.js` 的 `unlockByAd`）：以前解锁面板和充值页
各写了一份"没配就白送"，等于两处都在送，已经收敛成一处，两边行为不会再漂。

⚠️ **材料口径**：只有 `ADS.UNITS` 里填了广告位 id 且 `ADS.ENABLED = true` 时，
才是真的"看广告解锁"；没配时等于白送，**这时候提交材料里就不要写广告变现**。

### 13.5 解锁券（广告解锁凭证）

**系统说明**：
解锁券是**只能靠看广告获得**的免费解锁凭证。完整观看一次激励视频广告得 1 张；
免费次数用完后，消耗 1 张券即可进行一次性格图谱匹配。
券**不能用钱购买**、不可转让、不可兑换成货币或实物，也没有任何概率抽取成分。

#### 可直接复制的描述（按表单字数选一条）

**① 精简版（62 字，满足"最少 30 字"）**

**已经接上了**（两处都接，缺一不可）：
